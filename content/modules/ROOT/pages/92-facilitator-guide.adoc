= Facilitator Guide
:navtitle: Facilitator Guide

For facilitators provisioning participant clusters ahead of class. Participants can skip this page.

== What each participant cluster needs

One dedicated cluster per participant (15-20 for a full class). Each needs:

[cols="1,2,2",options="header"]
|===
| Prerequisite | Why | Check

| OpenShift 4.21 or later (Kubernetes 1.34+, tested on {ocp_version}) with OpenShift GitOps
| DRA's stable API, `resource.k8s.io/v1`, which every Module 2 manifest uses, is served from Kubernetes 1.34; Argo CD installs the workshop operators and the Showroom guide
| `oc get --raw /apis/resource.k8s.io/v1 >/dev/null && echo ok`; `oc get csv -n openshift-gitops-operator`

| OpenShift AI {rhoai_version}, DataScienceCluster with `kserve`, `modelregistry`, `dashboard` and `trustyai` Managed
| Modules 3 onwards (`trustyai` provides EvalHub and NeMo Guardrails for Day 3)
| `oc get datasciencecluster -o jsonpath='{.items[0].status.conditions[?(@.type=="TrustyAIReady")].status}'` prints `True` (and `Ready` likewise)

| One GPU node: AWS `g6.2xlarge` (1x NVIDIA L4 24 GB), tainted `nvidia.com/gpu=True:NoSchedule`, 200 GB root disk
| all GPU work; two model replicas share this one GPU on Day 2
| `oc get nodes -o custom-columns=N:.metadata.name,T:.spec.taints[*].key \| grep nvidia.com/gpu`

| CPU workers with room for the platform, a model registry, MaaS and (Day 3) a CPU safety model
| Days 2-3
| `oc adm top nodes`

| A default StorageClass
| model registry database, MaaS database, Showroom
| `oc get sc` shows one `(default)`

| One cluster-admin user per participant, with credentials handed out on the day
| participants act as themselves and change cluster-scoped configuration
| log in once as that user before class

| *No* `ClusterPolicy` on the GPU node, and no NVIDIA driver or device plugin already running
| Module 2 builds the DRA stack from scratch; the device-plugin stack must not manage the same node
| `oc get clusterpolicy` prints nothing
|===

To add the GPU node to an AWS cluster, `automation/gpu-machineset.sh` copies an existing worker
MachineSet, changes the instance type to `g6.2xlarge`, adds the taint and scales it to one. It
prints the MachineSet and asks before creating it.

== Provision

*RHDP:* order *Field Sourced Content - OpenShift Base* (`multinode`, OpenShift 4.22 or later,
*Select Base Workloads*: *OpenShift AI*; LiteMaaS and *Create users on cluster?* not needed) with
*Existing Gitops Repo?* checked:

[cols="1,2",options="header"]
|===
| Form field | Value

| GitOps Repo | `{lab_repo_url}`
| GitOps Revision | `main`, or an event branch
| GitOps Path | `automation/argocd`
|===

When the order shows *Running*, from a shell logged in as the order's `admin` user (the order
replaces kubeadmin with Keycloak SSO while it provisions):

. Nothing to do for the GPU node and OpenShift AI: on an RHDP order the chart's `order-prep` step
  sets `kserve`, `modelregistry` and `trustyai` to `Managed` on the order's DataScienceCluster and
  adds one `g6.2xlarge` GPU node (billed while it runs; the node joins in about 10 minutes). Watch
  `oc get jobs -n ws-order-prep` (both `Complete`) and `make -C automation verify`. If a Job fails
  (for example on AWS quota), do the same by hand: `bash automation/gpu-machineset.sh`, and
+
[source,bash]
----
oc patch datasciencecluster default-dsc --type merge -p '{"spec":{"components":{"kserve":{"managementState":"Managed"},"modelregistry":{"managementState":"Managed"},"trustyai":{"managementState":"Managed"}}}}'
----
. The guide is at `https://showroom-{showroom_namespace}.<apps domain>`, where the apps domain is
  the order's console URL without `console-openshift-console.`; the order page does not list it.
  Participants log in as the order's `admin` user.
. Web Terminal stops a session after 15 idle minutes (no keystrokes), even while a command runs,
  which can cut a long wait short. Each participant can raise it once in their terminal:
  `wtoctl set timeout 4h` (the terminal restarts).

*Any other OpenShift cluster*, from a cluster-admin shell in a checkout of this repository:

[source,bash]
----
make -C automation bootstrap                      # or PROFILE=<name>, see below
make -C automation status
----

Repeat `status` until every Application shows `Synced` and `Healthy`.

*Cluster profiles.* Clusters differ in which catalogs carry the operators. A profile is a values
file, `automation/argocd/values-<name>.yaml`, layered over `values.yaml`:

* `values-sandbox-ocp5.yaml`: OpenShift 5.0 pre-release clusters whose v5.0 catalogs lack the GPU
  Operator and NFD; it adds a v4.20 certified catalog and points each Subscription at a catalog that
  carries it. It also installs RHCL into an existing standalone Authorino operator's namespace,
  because a second Authorino in another AllNamespaces OperatorGroup conflicts with it.

== Verify every cluster

[source,bash]
----
make -C automation verify
----

Every line must print `PASS`. Fix any `FAIL` before participants arrive.

== Day of class

* Share the Showroom URL: `oc -n {showroom_namespace} get route showroom -o jsonpath='{.spec.host}'`.
* Hand each participant their cluster's console URL and user credentials.
* Day 1: Module 1 (15 min) runs in the 3:30-4:00 lab-instructions slot, Modules 2-3 (75 min) in the
  4:00-5:15 lab slot. Module 2's
  driver step takes about four minutes; Module 3's model start takes about five. Use the waits to
  explain what is happening.

* Day 2: Module 4 (55 min) runs in the 11:00-12:00 slot, Module 5 (50 min) in 2:00-2:50, Module 6
  (80 min) in 3:45-5:15. Each model recreate takes about three minutes. Module 5 Exercise 2 ends in
  HTTP 500 on purpose; Exercise 3 diagnoses and fixes it.

* Day 3: Module 7 (45 min) runs in the 1:15-2:00 slot, Module 8 (30 min) in 2:00-2:30, Module 9
  (50 min) in 3:10-4:00. The agent and evaluation jobs `pip install` packages and download a
  benchmark from the internet: the cluster needs egress to PyPI and Hugging Face.

== Known issues

* *RHCL installed after OpenShift AI.* KServe's `llmisvc-controller-manager` checks for the
  `AuthPolicy` CRD when it starts. If RHCL is installed later, `LLMInferenceService` resources stay
  `GatewayPreconditionNotMet: AuthPolicy CRD is not available` until that controller restarts:
  `oc rollout restart deployment/llmisvc-controller-manager -n redhat-ods-applications`.
  Install the workshop operators before class so this happens once, by you.
* *Model registry operator restart loop.* On a busy cluster the `model-registry-operator-controller-manager`
  can settle at about 210Mi, too close to its 256Mi limit: it stalls, misses its 1-second liveness
  probe and restarts every couple of minutes, and the DataScienceCluster reports `ModelRegistryReady=False`
  (`make verify` fails its DSC check). Raise its memory, which OpenShift AI preserves while the
  Deployment has no `opendatahub.io/managed: true` annotation (_Managing OpenShift AI_, "Customizing
  component deployment resources"):
  `oc set resources deployment/model-registry-operator-controller-manager -n redhat-ods-applications -c manager --requests=cpu=100m,memory=512Mi --limits=memory=512Mi`.
  To return to the defaults, add the annotation `opendatahub.io/managed=true` to the Deployment.
* *Web Terminal stops when idle.* The Web Terminal's workspace stops after a period without input
  (15 minutes by default, per the Web Terminal documentation; the *Initialize terminal* panel's
  *Timeout* option sets a longer one). Seen on the test cluster during a long recording session. Shell
  variables and helpers are then gone: participants re-run the current module from its first
  exercise (see _How the exercises build on each other_ on the Prerequisites page).
  The timeout is `WEB_TERMINAL_IDLE_TIMEOUT` (default `15m`) in the `web-terminal-exec` template in
  `openshift-operators`. To lengthen it, each participant runs this in their own terminal (Web
  Terminal's `wtoctl` changes only the caller's workspace; the terminal restarts once). Verified on
  the RHDP order: the workspace then carries `WEB_TERMINAL_IDLE_TIMEOUT=4h`.
+
[source,bash]
----
wtoctl set timeout 4h
----
* *DNS for `maas.<domain>`.* The ingress operator publishes the record within seconds and the Web
  Terminal resolves it at once; laptops with cached negative answers may need several minutes.
* *User-workload monitoring.* Module 5 enables it. If the cluster already has a
  `cluster-monitoring-config`, participants must add `enableUserWorkload: true` to it rather than
  replace it.
* *GPU Operator catalog on OpenShift 5.0 pre-release.* The v5.0 certified index does not carry
  `gpu-operator-certified`; use the `sandbox-ocp5` profile.

== Cost

Each participant cluster runs one `g6.2xlarge` for the length of the event, in addition to its CPU
nodes. Scale the GPU MachineSet to 0 between days if the event allows a daily rebuild of Module 2,
and delete it after the event.
