From a bare GPU node to a governed, observed, evaluated and guarded AI service on OpenShift AI,
built by you, one layer at a time.

This workshop is the hands-on half of a three-day field enablement event. The presentations
explain the product; the labs make you build it. On your own OpenShift cluster with one NVIDIA L4
GPU, you write and apply every resource yourself: the GPU driver and Dynamic Resource Allocation,
the model registry and model server, llm-d, Models-as-a-Service, tracing, evaluation and
guardrails. Each step states what must be true afterwards, and you check it against what the
cluster reports. By the end you can explain to a customer not just what OpenShift AI does, but how
each layer does it and how to prove it.

The labs progress through these tasks:

. Make a GPU schedulable with the NVIDIA driver and Kubernetes DRA, and claim it exclusively and
  shared (Day 1).
. Find a validated model, record it in a model registry, and serve it with vLLM behind
  authentication (Day 1).
. Replace the single server with llm-d and see its scheduler route requests (Day 2).
. Stand up Models-as-a-Service and publish the model with tiers, keys, limits and usage telemetry
  (Day 2).
. Trace an agent with MLflow, evaluate the model, and guard it with NeMo Guardrails (Day 3).

== Learning objectives

By the end of the workshop you will be able to:

* Explain and demonstrate how a Kubernetes workload gets, and shares, a GPU through DRA.
* Onboard a model from the catalog through the registry to an authenticated vLLM endpoint.
* Explain what llm-d's scheduler adds over a single vLLM and show it routing.
* Stand up Models-as-a-Service and govern access with subscriptions, API keys and rate limits.
* Trace, evaluate and guard a model-backed application with MLflow, EvalHub and NeMo Guardrails.

== How to run the lab

Each exercise names the state to change, the evidence to inspect, and the result that must be
verified. Do not treat command completion as proof. Compare the observed resource, field or event
with the stated expected result before continuing. Facilitators: see
xref:92-facilitator-guide.adoc[Facilitator Guide].

== Technical model

* *GPU layer:* the NVIDIA driver makes the GPU work on the node; the NVIDIA DRA driver publishes it
  as a described device; the Kubernetes scheduler allocates it to claims.
* *Model layer:* the model catalog lists validated models; your model registry records the
  versions you use; KServe runs vLLM, which turns GPU memory into weights plus KV cache.
* *Routing layer:* llm-d's endpoint picker chooses a replica per request from live server state.
* *Service layer:* Models-as-a-Service, enforced by Red Hat Connectivity Link (Kuadrant) on a
  Gateway API gateway, turns a model into a governed internal service with keys, tiers and limits.
* *Trust layer:* MLflow traces what an application did, EvalHub measures model quality, and NeMo
  Guardrails decides what may reach the model.

No single layer answers the customer's whole question. A GPU claim does not authenticate anyone, an
API key does not prove the model is accurate, and a benchmark does not stop a harmful prompt. The
workshop builds all five so you can show where each guarantee comes from.
